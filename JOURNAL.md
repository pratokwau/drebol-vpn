# Журнал действий ассистента — Drebol VPN

Этот файл ведёт ассистент (муся) для контроля: что сделано, что решено, что сломалось и что осталось открытым. Читать может пользователь и любой другой ИИ, который будет работать с проектом, — отсюда должна быть понятна и картина сервиса, и история изменений.

Правила ведения: первая часть — актуальное описание сервиса (обновляется, когда меняется сама архитектура). Вторая часть — записи по дням: что случилось → что сделали → что решили → результат → что осталось открытым. Обновление — каждый день в 23:59 (МСК). Честно фиксируются и неудачи.

## Часть 1. О сервисе

**Drebol VPN** — сервис продажи VPN-подписок. Владелец и оператор — пользователь (pratokwau). Продажи и управление — через Telegram-бота **@drebolvpn_bot**, поддержка — отдельный бот и форум-группа поддержки.

### Продукт и код
- Репозиторий: pratokwau/drebol-vpn (GitHub), все изменения — сразу в ветку main.
- Основной бот: python-telegram-bot, polling; внутри того же процесса — веб-кабинет (Mini App) и веб-админка на aiohttp. Главная админка — Telegram-бот, веб-админка — дополнение.
- Панель управления пользователями и нодами: **Remnawave** (panelremna.drbl.tech).
- Оплата: Platega. Подписки пользователям выдаются по ссылке sub.drbl.tech (через Yandex CDN); origin подписки — key.drbl.tech (не трогать).
- Сайт и кабинет: vpn.drbl.tech.
- Поддержка: отдельный процесс (support_bot.py), тикеты — темы в форум-группе; одна тема на пользователя навсегда, /close меняет только статус и иконку темы.

### Инфраструктура (состояние на 2026-11-23)
- **Выходы (exit-ноды):** Германия (VPSPay, 144.31.223.252 — главный сервер: панель, бот, сайт), Швеция (NodeHost, 81.90.21.84). Финляндия (95.85.251.169) — аренда заканчивается 2026-11-24 01:09, не продлевается.
- **Мосты (точки входа для РФ):** мост-1 — Латвия (HostVDS, Рига, 31.59.168.90, домен most4.tembadr.tech); мост-2 — Oblako (187.54.0.243, most2.tembadr.tech, резервный, с потолком скорости и трафика).
- **Схема выдачи (с 2026-11-22):** на каждую страну — 4 хоста: мост Латвия, мост Oblako, прямой, [LTE]. Транспорт мостов — только VLESS XHTTP Reality; прямые — VLESS TCP Reality; LTE-линейка — XHTTP через Yandex CDN (пользователь → Yandex CDN → основная нода). Плюс автовыборы: обычный (по скорости загрузки, балансирует между XHTTP-хостами обоих мостов) и [LTE].
- Домены: drbl.tech (сайт, подписка, CDN) и tembadr.tech (ноды и мосты); обе зоны DNS — SpaceWeb.

### Контент
- TikTok @drebolvpn: 3 видео в неделю (пн/ср/пт ~19:00–21:00 МСК), производит автономный агент по расписанию, публикует только пользователь.

### Автономные агенты ассистента
- Веб-админка: агент-улучшатель каждые 2 часа правит только web/ в main, полными фичами, с тестами; деплой не делает.
- TikTok-продюсер: каждые 48 часов ведёт контент-план и производит одно видео.
- Синхронизация с панелью — только вручную (решение пользователя); исключение — утренний прогон тегов в 09:00.

### Доступы ассистента
- Панель Remnawave и админки — через облачный браузер (логины в Secure Vault; деплойные кнопки с confirm() нажимает только пользователь).
- Серверы по SSH: прямой SSH из среды ассистента закрыт сетевым фильтром; доступ — через Tailscale (устройство «muse» в tailnet владельца) + публичный ключ ассистента в authorized_keys.

### Стоящие правила
- Перед командами, меняющими серверы (пакеты, фаервол, конфиги), ассистент называет состав и побочные эффекты и спрашивает подтверждение; read-only диагностику делает сам.
- Внутренние детали инфраструктуры (IP, мосты, схема) не попадают в публичный контент.
- Названия хостов и UUID сверяются только по карточкам в панели, не по отчётам агентов.

**Код и админки (день).**
- Исправлена статистика «база vs панель»: счётчик панели раньше считал служебных bridge-пользователей обычными клиентами; коммит в main, после деплоя ожидается «94 клиента, совпадает».

- Веб-админка (автономные проходы): экраны «Напоминания и возврат», «Техработы и функции», карточка «Бот поддержки», переключатель периода графиков 7/30 дней. Всё в main, деплой — за пользователем.

**Инцидент (вечер).** У пользователя на мобильном интернете (МТС, Москва) перестали работать ВСЕ хосты — мост, прямые и LTE; по Wi-Fi всё работало. Проверки с проводных российских нод показывали полную доступность — резался именно мобильный сегмент. Телефонные тесты без VPN показали: МТС на мобильном режет наши европейские IP поадресно (не DNS, не SNI, не порт — по прямому IP главный сервер тоже не открывался). Отдельной «волны блокировок» 20–22.11 в открытых источниках не нашлось; рабочий механизм — поадресные блокировки + заморозка соединений ТСПУ на малом числе пакетов на мобильном.

**Ремонт LTE/CDN.** Пользователь разрешил работу с LTE-системой (обычно под запретом). Нашлось две поломки: (1) в DNS отсутствовала запись de1cdn — немецкая LTE-цепочка умирала на резолве; запись восстановлена, «Германия [LTE]» ожила сразу; (2) на финской и шведской нодах в nginx не было location для CDN-пути — пользователь по выданным конфигам создал сайты, после чего ожили все LTE-хосты. «Welcome to nginx» на голом cdn-домене — норма, не поломка.

**Миграция на CDN-only.** По решению пользователя («Франция не нужна: пользователь → Yandex CDN → основная нода») выдача переведена на CDN-хосты, мостовые и прямые отключены (не удалены). Сервер Франции пользователь затем удалил сам; нода Франции удалена из панели. Попутно проверен биллинг Yandex CDN: 4 ресурса × 150 ₽/мес, сейчас полностью покрыто грантом 2 650 ₽, к оплате 0 ₽; ставка за сверхпакетный трафик в консоли не видна — открытый вопрос.

**Латвийский мост.** Пользователь купил VPS в Риге; первый IP сканер показал заблокированным ТСПУ до начала работы — сервер заменён. Актуальный: 31.59.168.90 (HostVDS). Ноду пользователь создал сам и поставил ПО; ассистент назначил профиль BRIDGE-AMS 9/9. DNS most4 перевешена на новый IP.

**План «4 хоста на страну» (решение пользователя, собрано в панели к 23:41).** На страну: мост Латвия + мост Oblako + прямой + [LTE]; мосты — только XHTTP. Хосты Oblako пересозданы (удалялись 21.11), прямые включены обратно, хост «Германия #1 [443]» удалён полностью, TCP-хосты мостов оставлены выключенным резервом. Порядок: основные сверху, LTE-блок снизу. Приписки [LTE] возвращены LTE-хостам и их автовыбору (откат переименований миграции — по приказу пользователя). К 23:55: обычный автовыбор возвращён первым в списке, его шаблон переведён на 6 XHTTP-хостов обоих мостов; «Автовыбор [LTE]» перемещён под LTE-серверы; основные хосты переименованы в «Германия/Швеция/Финляндия 1/2/3» (дубли «#2» давали в клиенте хвосты ^~2~^).
